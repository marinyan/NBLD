# 後続テープからのストリーミング展開

`-Transport Tape -PayloadBaud 600` または `1200` を指定すると、先頭は
小さな N-BASIC ローダー（常に600 baud）、後続は圧縮したNBLD v3パッケージになる。
`CLOAD"NBLD80"` → `RUN` の操作は同じ。省略時の `Embedded` は従来方式で、
既存パッケージ・BASIC・CMT/T88との互換性を維持する。

ゲームごとの受信コードは不要。作品名・配置セグメント・entry・速度を指定する。
ROM裏のentryには `-EntryMemoryControl 2` を指定する（既定0）。

同時に `*-monitor.t88/.cmt` も生成する。こちらは `MON` → `L` → `G8800`。
8800Hの小さな転送stubが、BASIC版と同一の受信コードをF500Hへ移して実行する。
後続本体も同じで、MON用の独立したゲーム別ローダーは不要。

## メモリ

- BASIC初段は受信・展開コードをC8C0Hへ復元し、F500Hへ移す。
- 実行中の保護領域はF500H〜FAFFH。スタック上端はFB00H、最低64バイトを予約。
- 圧縮データ全体をC800Hへ受ける領域も、BASIC内の本体Base64も不要。
- 受信したLZSSトークンから直接配置先へ展開する。辞書は既に展開した同一セグメント。
- MemoryControlは0または2。ROM裏は2で指定する。別VRAMプレーンの直接ロードは未対応。
- NBLD v3の16bit総長は維持するため、圧縮パッケージは最大65,535バイト。
- `-AllowLoaderOverwrite` は既存の最終コピー方式を使用する。保護領域に重なるデータを
  未使用RAMへ一時配置し、全検査成功後にスタックを使わず最終コピーする。
  コピー用コードと保留データの空き領域は依然必要で、任意の全64KB配置を保証しない。

## テープ形式（NBLD tape transport v1）

1. 同期8バイト：ASCII `NBLDT`、01H、A5H、5AH。
2. NBLD v3固定ヘッダー32バイト＋entry時のport31H値1バイト＋その33バイトのCRC16。
3. 各セグメントについて、v3記述子8バイト＋CRC16、LZSSデータ＋CRC16を順に格納。

CRCはCRC-16/CCITT-FALSE（1021H、初期FFFFH、非反転）、little endian。
記述子はCRCが一致してから使用する。実行時も長さ・アドレス周回・ローダーとの重なり・
メモリ設定・LZSS参照距離・展開長・圧縮長・パッケージ総長を検査する。
破損データがRAMへ一部書かれる場合はあるが、エラー時はentryへ移らない。巻き戻して
リセットから再試行する。RAM内容のロールバックは提供しない。

USARTエラー、バイト待機タイムアウト、同期検索上限でもモーターを止めてHALTする。
診断用F503Hは0=正常、1=タイムアウト、2=USART、3=CRC、4=形式、5=配置、6=LZSS。
F504Hは1=同期/ヘッダー待ち、2=展開中、3=成功、FFH=失敗。ゲーム起動後は再利用可能。

T88は600/1200と各区間の4800Hz tickを保持する。CMTは同じデータ列だけで速度情報を
持たないため、混在速度の音声化にはT88を使う。T88のデータタグは最大32,768バイトで分割。
ビルド結果の `TapeSeconds` はキャリア・無音・末尾込みのテープ長であり、操作・展開待ちは含まない。

## 実機での扱い

1200版は対応するPC-8001mkII向け。初代8001やmkIISRまで一律に1200対応とは扱わず、
600互換版も残す。エミュレーターはUSART速度設定を厳密に照合しないため、
M88Vでの成功は実機の音声入力成功を証明しない。実機1200 baudは別途検証が必要。

リモート端子付きレコーダーはCLOAD完了の停止・RUN後の再開に従う。
PC/スマートフォンからの音声再生ではCLOAD完了時に一時停止し、RUN後に再開する。
初段の後ろに短いキャリアを設けるが、手操作とBASIC実行がその時間内に終わるとは仮定しない。

ローダーとスタックの最終コピー、CRC・長さ・参照距離・配置・途中切れの異常系を検査する。
ゲームの速度変更は行わず、テープ受信の機能確認として扱う。

## ロード進捗表示（2026-10-22）

テープ方式はヘッダー検証後、先頭行へ `LOAD BLOCK 000/171` のように表示する。
分母は固定ヘッダーを除くパッケージ長を256バイト単位で切り上げた値。
セグメント記述子と圧縮データを数え、同期列・ヘッダー・伝送CRCは含めない。
256バイト受信ごとに分子を更新し、全CRC検証成功時は端数を含め分母まで進める。
これはディスクのセクタ番号ではなく、テープ受信量の目安である。

BASICの40/80桁設定やスクロール位置に依存しないよう、モーター始動前に80桁・25行、`F300H`始点のCRTC/DMA設定へそろえ、ヘッダー検証後に先頭行を初期化する。
表示は文字VRAMへ直接書き、ROM呼出しや割り込みは使用しない。
ロード先が表示文字のF300H〜F311Hに重なる場合、そのセグメントの展開前に
以後の表示更新を停止する。既存の配置範囲を狭めず、ロード済みの本体を壊さない。
従来のEmbedded方式、パッケージ形式、後続テープ本体、CRC、ゲームデータは変更しない。
初段受信器が大きくなる分だけ600 baudの初段ロード時間は増える。

`tests/streaming.ps1`は途中進捗、端数を含む完了表示、表示領域の両端と直後への
ロードを検証する。通常受信、600/1200 baud、MON、ROM裏、最終コピー、異常系も対象。
検証結果：M88V N802で既存19ケース＋進捗5ケースが成功。
受信器は769→1,057バイト（+288）、FB00Hまでのスタック空間479バイト
（最低予約64バイトを除いた余裕415バイト）。z80asmとSjASMPlusで受信器が一致。
他作品の検証はDefender80（PC80/MK2/MK2FULL）、StarWars80、SKYKID80の
5構成×600/1200 baud。既存本体を新旧ビルダーに通し、パッケージと伝送本体が
全バイト一致することを確認。新受信器の展開後に検査用entryで停止させ、
本体全バイトを比較（SKYKIDのROM裏512バイトはCPUで上位へコピーして比較）。
ゲーム開始後の操作テストとは区別する。旧Embedded方式のDefender80についても
package/BASIC/CMT/T88/受信器の全バイト一致を確認。
他作品の固定submoduleは自動更新せず、Rogue80で先行採用する。
